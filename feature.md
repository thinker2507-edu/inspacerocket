## Architecture and data flow

`setup()` initializes serial/buses/sensors/radio/SD and begins asynchronous flash recovery; rocket first drives both servo signals LOW. Radio failure no longer halts sensors/logging/USB commands. `loop()` services USB and LoRa, GPS/queued IMU reports, checked RTC, journal/recovery, INA and camera, then the 20 ms flight block. SD work is scheduled outside busy radio periods; card operations remain synchronous and can stall.

BMP pressure and gravity-projected IMU acceleration feed the existing vertical estimator; fresh/quality-checked data controls stationary/calibration/arming/flight logic. Local `FlightImu.h` preserves bundled SH-2 reports and supplies the receive timestamp missing in the installed library's I2C transport. Telemetry axes deliberately hold latest decoded values independently of flight-quality gates; a stale cached value is not proof of a healthy IMU. Missing initial axes are NaN. Existing explicit gyro offsets remain applied.

Sensors -> estimator/state machine -> current snapshots -> 5 Hz SD CSV; sparse checkpoints/events/calibration/counter reservations -> external NOR. Telemetry formatter -> reservation gate -> radio/USB. GCS -> existing keyed/checksummed envelope -> direct USB or ESP32 bridge -> common dispatcher -> same-connection ACK, including delayed completion. See `commands.md` for the short serial command list and `COMMAND_PROTOCOL.md` for framing, results, restrictions and effects.

## Flight states and servo behavior

Launch tuning is now isolated in each target's local `LaunchConfig.h`, including the previously inline fallback altitude/velocity and rising-speed threshold. Existing numerical values and conditions are unchanged; no runtime command or adaptive threshold was added. Configuration is compile-time checked for coherent altitude/speed limits and sample-counter bounds; this does not qualify thresholds for flight. `LAUNCH_ACCEL_G=2.5` retains the inherited total-g-equivalent convention: actual gravity-compensated vertical acceleration comparison is >1.5 g. Rocket and CanSat configs are independent; the CanSat's inherited thresholds still require its own launch/release-profile validation. Pad-relative altitude calibration remains automatic; a fixed absolute site altitude is not assumed.

Rocket `FlightState` now explicitly assigns every existing numeric ID (0..5) and asserts the mapping at compile time. Wire/journal IDs, GCS labels and transition behavior are unchanged; readable constants remain in control logic. See [REJECTION_GUIDE.md](REJECTION_GUIDE.md) for the current GCS/rocket validation, rejection, deferred failure and automatic-action inhibition inventory, including source functions and IMU thresholds. No safety restriction or command was changed for this documentation update.

Wire states remain 0 PAD, 1 POWERED_ASCENT, 2 COAST, 3 APOGEE, 4 PARACHUTE_DESCENT, 5 LANDED. Startup is PAD/unarmed. Explicit ARM, durable ARM record and reference acquisition gate launch. Existing ascent/burnout/apogee/landing logic is unchanged. Apogee requires repeated fresh accepted baro observations below the tracked maximum with nonpositive velocity; APOGEE holds 1000 ms before DESCENT. That hold does not add a fresh descent sensor check. The existing thresholds/detector have software checks but no demonstrated flight qualification for actuation; no new detector/threshold was invented.

The rocket servo controller reserves one automatic attempt only for the existing **APOGEE -> DESCENT** transition with a launched mission, completed recovery and no recovery hold. It sets `RF_SERVO_INTENT=524288` in the existing 128-byte version-2 STATE snapshot, waits for its NOR commit, then commands each independently enabled/confirmed deployment output once. A commanded result adds `RF_SERVO_COMMANDED=1048576` in a later STATE snapshot. Flags describe intent/issued PWM, never physical deployment. CSV schema, telemetry schema, state numbering and journal record layout are unchanged. Repeated hardware pulses hold a target; the automatic action does not issue repeated target changes.

On recovery, prior intent, descent/landed state, damaged/torn records or recovery ambiguity inhibit automatic replay. No startup neutral is issued for recovered active/ambiguous missions. A clean pre-descent recovery with no intent/ambiguity may still act on its later normal descent transition. Queue/storage failure or 5 s commit timeout commands no deployment; a commit-to-output reset may skip deployment. This is at-most-once command behavior, not an exactly-once physical guarantee. Only an explicit new ARM mission or durably completed RESETPAD resets the automatic latch; manual tests/status never do. Servo actions never change mission clock/state. Loss of PWM on reset may itself affect the mechanism; that behavior is untested.

### Current servo configuration and testing

The user confirmed **PWM4 is a continuous-rotation MG995**. PWM4 remains Teensy pin22, 50 Hz, bounded 1000..2000 us. New existing-protocol arguments `PWM4 SPIN` (configured 1700 us), `PWM4 REVERSE` (1300 us) and `PWM4 STOP` (safeUs, nominal 1500 us) control rotation until another accepted command. These are nominal bounded test drive values, not calibrated speed, measured direction or verified stop. Trim safeUs for actual neutral if needed. There is no feedback or calibrated one-revolution timing: do not claim an exact 360-degree turn or add a guessed run duration. No automatic stop timer exists.

**PWM5 remains independently controllable** on pin23 with its previous 50 Hz, 1000..2000 us positional/manual pulse profile; TEST90 and SAFE remain nominal 1500 us. It rejects the new continuous-only keywords. PWM4 TEST90 is preserved for compatibility as a 1500 us neutral request, not a 90-degree movement. The previous neutral TEST90 can explain no visible motion on a continuous servo, but does not establish the cause of the previously reported wireless timeout. Numeric commands still work on either output. `STATUS SERVO` adds C4=1/C5=0 configured-type flags; these are not measured hardware identification or position feedback.

Use the existing GCS command input with the normal authenticated LoRa/ACK path, or optional `servoCommands.spin()`, `.stop()`, `.reverse()` (PWM4 only), `.pulse(5,1200)` and `.safe(5)`. No GCS layout/buttons changed. One command at a time; wireless requests retain acceptance ACK then DONE/FAIL. The updated rocket firmware must be installed before the new keywords work. Motor motion, RPM, exact stop and physical wireless operation remain unverified. The complete updated tests/verify.ps1 passed after this continuous-servo change, including actual C++ spin/stop/reverse parsing and channel isolation, actual wireless dispatch/ACK/DONE simulations for SPIN/STOP/REVERSE and independent PWM5 pulses, browser snippet encoding, existing regressions, both Teensy ARM object configurations and receiver syntax/API compilation.

The independent configuration rows in `finalfsw/ServoControl.h` set type, pulse bounds, neutral, spin/reverse, safe/deploy positions and confirmation flags. `startupSafeConfirmed=false` and `deploymentConfirmed=false` remain unchanged per output; startup remains LOW and no automatic deployment output is enabled. Output now uses the bundled Teensy `Servo.h` API from `servotestting/servotestting.ino`, isolated in the existing `ServoControl.h`: two independent Servo objects, lazy `attach(pin,500,2500)` and `writeMicroseconds(us)`.
